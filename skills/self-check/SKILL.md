# 이력서 셀프 점검

TRIGGER — `/self-check` 호출 시 이 스킬을 로드.

이력서 초안을 제출 전 아래 6가지 기준으로 점검하고, 프로젝트별로 구체적인 수정 지점을 짚어 보고한다. **이력서 파일을 직접 수정하거나 대신 다시 쓰지 않는다.**

## 점검 기준

### 1. 문제 → 해결 → 성과 구조

- 각 프로젝트가 "문제 상황 → 취한 해결 → 성과" 순으로 읽히는가?
- 성과 문장이 없는 프로젝트는 최우선 수리 대상. "무엇을 했다"로 끝나는 항목이 있는지 찾는다.

### 2. 숫자 커버리지

- 프로젝트마다 숫자가 하나도 없는 항목이 있는가?
- 정확한 지표가 없다면 규모(사용자 수, 트래픽, 코드량)나 전후 비교(개선 전/후)라도 넣도록 제안한다.
- 프론트엔드 관점 지표 예시: Web Vitals(LCP/CLS/FCP), 번들 크기·빌드 비용 절감, Amplitude/GA 등 유저 행동 데이터, 이미지·폰트 최적화 수치.

### 3. 메타데이터 정형화

- 각 프로젝트에 기간, 역할(기여도), 기술 스택이 개요 형태로 명시돼 있는가?
- 본문 서술에 흩어져 있지 않고 스캔 가능한 요약 블록으로 분리돼 있는가?

### 4. 형용사 대신 수치

- "꼼꼼하게", "열심히" 같은 형용사·부사 표현이 남아있지 않은가? 있다면 수치나 구체적 사실로 치환할 것을 제안한다.

### 5. 10초 스캔 생존 구조

- 문서를 10초만 훑어도 "이 사람이 뭘 했는지" 파악되는가? (읽기 순서는 스캔 → 정독 → 검증이며, 스캔 단계를 먼저 통과해야 함)
- 프로젝트가 소단위로 분리돼 있는가 (하나의 거대한 서사 덩어리가 아닌지)?
- 메타데이터 요약 + 문제-해결-성과 포맷이 함께 있는가?

### 6. 서사형/나열형 탈락 패턴

- 4장을 써도 "그래서 이 사람이 뭘 하고 싶었던 거지?"란 반응이 나올 법한 대하사극식 서술이 있는가?
- 단순 나열("~를 했습니다"의 연속)로 읽히는 구간이 있는가? 있다면 문제-해결-성과 포맷으로 재구성 제안.

## 출력 형식

```
## 이력서 셀프 점검 결과

**판정: PASS / FAIL** (최우선 수리 대상이 하나라도 있으면 FAIL)

### 프로젝트별 체크
- {프로젝트명} — 문제/해결/성과: OK / 성과 누락(최우선 수리) / 서사형(재구성 필요)
  - 숫자: {있음 / 없음 — 없으면 대체 지표 제안}
  - 메타데이터(기간/역할/스택): {명시됨 / 누락}

### 지적 사항 (심각도순)
- `[최우선]` {프로젝트/항목} — {문제} → {고칠 방법}
- `[개선]` {프로젝트/항목} — {문제} → {고칠 방법}
- `[nit]` {프로젝트/항목} — {문제} → {고칠 방법}
(없으면 "없음")
```

## 규칙

- 읽기 전용: 이력서 파일을 수정하거나 대신 다시 쓰지 않는다. 제안만 한다.
- 지적에는 반드시 프로젝트명(또는 섹션명)을 포함한다.
- 성과 없는 프로젝트, 숫자 0개 프로젝트는 무조건 `[최우선]`으로 분류한다.

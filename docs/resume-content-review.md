# 이력서·포트폴리오 내용 검토 체크리스트

이 문서는 공개 이력서와 포트폴리오의 표현을 최종 확정하기 전에 사실관계와 면접 답변 범위를
확인하기 위한 작업 메모다. 확인한 항목은 체크하고, 결정한 문구를 각 항목 아래에 적는다.

## 우선 확인

### 안경사 통합관리 시스템 배포 성과

- [ ] `프론트엔드 독립 배포 구조`가 실제 구조를 정확히 설명하는지 확인
- [ ] 기존 약 20분과 변경 후 1분 30초의 측정 기준이 같은지 확인
- [ ] 배포 시간 단축에 직접 영향을 준 변경 사항 확인
- [ ] 해당 구조에서 직접 설계하거나 구현한 범위 확인

현재 공개 문구:

> 15,000줄 제품판매 JavaScript를 기능 단위 React 구조로 전환하고 프론트엔드 독립 배포
> 구조를 구축해 운영 배포 시간을 약 20분에서 1분 30초로 단축

면접에서 설명할 내용:

- 기존 배포 과정: 프론트 코드만 변경 시에도 백엔드까지 한번에 배포해야되는 상황이었음 (JSP, JS만 변경 시에 해당 부분만 말아서 배포하도록 분리하 할 수 있었지만, 이미 코드가 10년정도 된 레거시여서 프론트를 react로 전환하기로 결정함)
- 변경한 배포 과정: 백엔드는 API 쪽만 담당 / 프론트는 React로 전환하여 레파지토리 자체가 분리됨
- 직접 담당한 작업: JSP -> React 프로젝트 리뉴얼 작업
- 시간 측정 방법: 젠킨스 배포 시작-완료 시간으로 측정

### 렌즈 시뮬레이터 기간

- [ ] 시작일을 `2024.11`과 `2024.12` 중 하나로 통일

현재 사이트 프로젝트 데이터는 `2024.11`, career-wiki 프로젝트 문서는 `2024.12`로 서로 다르다.

확정 기간: 2024.11

### 논마이아큐브 인보이스 성과

- [ ] `약 70개 안경원`의 집계 기준 확인
- [ ] `300만 원 이상의 인보이스`가 매출, 청구액, API 사용료 중 무엇인지 확인
- [ ] LOT 스캔 기능과 인보이스 발생의 관계를 설명할 수 있는지 확인

인과관계가 간접적이라면 다음처럼 범위만 제시하는 편이 안전하다.

> 약 70개 안경원이 참여한 프로모션의 구매 LOT 스캔·본인인증 흐름을 구현

제안 준 것 처럼 범위만 제시하는 쪽으로 하는게 좋을 것 같음

## 역할 표현

### 리더십 범위

- [ ] 파트 리더 경험은 삭제하지 않고 이력서의 핵심 강점으로 유지
- [ ] `개발·운영 총괄`이 직책과 실제 권한에 맞는지 확인
- [ ] `주도`라고 표현한 프로젝트마다 본인이 결정한 범위를 설명할 수 있는지 확인
- [ ] 업무 배분, 일정 관리, 기술 검토, 코드 리뷰 중 실제 수행 항목을 구분
- [ ] `신입 개발자 멘토링`의 대상, 기간, 구체적인 지원 내용을 확인

`팀 생산성 향상`, `개발 효율성 강화`, `배포 안정성 확보`처럼 결과가 추상적인 표현은 근거가
없다면 수행한 행동으로 바꾸는 편이 좋다.

예시:

- 변경 전: 팀 업무 배분과 의사결정 지원으로 팀 생산성 향상
- 변경 후: FE 3명의 업무를 배분하고 라우팅·결제·정적 리소스 규칙을 문서화

### 업무 분배 경험 작성

아래 내용을 구체적으로 채운 뒤 이력서의 리더십 문장으로 정리한다.

- 팀 구성과 각 팀원의 숙련도·담당 영역:
- 프로젝트 시작 시 전체 업무를 나눈 기준:
- 화면, 기능 또는 기술 난이도를 판단한 방법:
- 팀원별 업무를 배정할 때 고려한 요소:
- 본인이 직접 맡은 영역과 팀원에게 위임한 영역:
- 일정과 우선순위를 정한 기준:
- 기획·디자인·서버팀과 선행 조건을 조율한 방식:
- 진행 상황을 확인한 주기와 방법:
- 일정 지연이나 기술적 어려움이 발생했을 때 업무를 다시 조정한 사례:
- 팀원이 막혔을 때 코드 리뷰, 페어링, 문서 중 어떤 방식으로 지원했는지:
- 리더의 결정으로 달라진 결과:
- 다음 프로젝트에서 업무 분배 방식을 바꾼 경험:

이력서 문장 후보:

> 아큐브 전사 서비스의 프론트엔드 파트 리더로 FE 3명을 이끌며 요구사항 정의, 업무 배분,
> 일정 조율과 기술 의사결정을 담당

> 6개 사용자 역할과 60개 이상의 화면을 기능·난이도·선행 API 기준으로 나누고, 팀원별 경험과
> 일정을 고려해 업무를 배분

두 번째 문장의 `기능·난이도·선행 API`, `팀원별 경험과 일정`은 실제 업무 분배 방식과 일치하는지
확인한 뒤 사용한다.

### 기여도 표기

- [ ] 안경사 통합관리 시스템 `기여도 30%`의 산정 기준 확인
- [ ] 렌즈 시뮬레이터 1차 `FE 단독 100%`, 2차 `기술 검토 5%`의 기준 확인
- [ ] 채팅 v2.0 `진행률 90%`가 프로젝트 완성도인지 본인 작업 진척도인지 확인

기여도 숫자는 눈에 잘 띄지만 산정 근거가 불명확하면 역할과 담당 범위를 직접 쓰는 편이 더
설득력 있다.

## 기술 표현

- [ ] `AWS Pipeline`의 실제 서비스명이 AWS CodePipeline인지 확인 후 명칭 통일
- [ ] `AWS Text 스캔 API`의 정확한 제품명 확인
- [ ] Spring Security 문제에서 직접 적용한 임시 조치와 백엔드팀이 적용한 정식 조치를 구분
- [ ] `독립 배포`, `동시 운영`, `점진 전환`이 서로 다른 두 회사의 경험과 섞이지 않았는지 확인

## 제외하기로 한 내용

- Sentry 대시보드 관련 프로젝트와 기술 표기는 공개 이력서·포트폴리오에서 제외한다.
- 이유: 대시보드 구성 범위를 넘어 모니터링 체계 구축·운영 전반을 담당한 것으로 읽힐 수 있고,
  면접에서 깊이 있는 답변이 어려움.

# 프로젝트 상세 내용 보강 가이드

현재 PDF와 `career-wiki`를 비교해, 채용 담당자가 역할과 성과를 판단하기 위해 추가 정보가
필요한 프로젝트를 우선순위별로 정리했다. 브라더메이즈 경력은 제외한다.

## 우선 작성 권장

### 1. 가상피팅 - '안경사/산학 협력용 렌즈 판매 시뮬레이터 프로젝트'

상태 관리 구조를 단계적으로 개선한 과정이 좋아 프론트엔드 설계 역량을 보여주기 적합하다.

- 정확한 개발 기간
- 팀 구성과 본인 역할·기여도
- Context API와 Funnel을 함께 사용하게 된 배경
- 리렌더링 문제의 관찰 방법과 영향 범위
- Zustand 분리 및 `overlay-kit` 적용 후 달라진 결과
- 사용자 수, 대상 안경점 수, 오류 감소 등 공개 가능한 결과

```text
기간: 2024.11 - 2025.02 (1차), 2026.04-2026.05 (2차)
팀 구성 / 역할 / 기여도:
    - 1차: 기획 1, BE 2, FE 1 / 프론트엔드 전반적인 개발 업무 / 100%
    - 2차: 기획 1, BE 1, FE 2 / 프로젝트 관련 내용 인수인계 및 하드코딩된 영역에 대한 백엔드팀과의 의사결정 도움, 기존 모달의 문제점 전달 및 overlay-kit 적용을 위한 기술 검토 및 의사결정 / 5%
사용자 또는 운영 규모: 1차: 안경사 (10곳 -> 2곳 줄어듬), 2차: 안경사 + 산학협력 (배포 후 퇴사로 인해 수치 확인 불가)
문제:
    - 게임을 시작함과 동시에 서버에서 모든 대화와 문제에 대한 컨텍스트를 한번에 내려줘서 거대한 데이터를 다뤄야하는 했음
        - 거대한 데이터를 프론트에서 대화/문제/스텝별로 구분하여 뿌려줘야해서 굉장히 복잡했고, object depth도 굉장히 깊어서 zustand의 Immer로 처리를 했지만 유지보수함에 있어서 문제가 있다고 판단함 -> object 구조를 좀 더 세분화해서 분리 해야했다고 생각함 (실패경험)
    - Step으로 구성되어있어서 Context 와 Funnel로 구현했는데, 새로고침 시에도 유지가 되어야해서 zustand로 모두 변경 처리함
    - 타이핑 애니메이션이 적용되어있던 안경사/고객의 메세지 박스가 모달이 온/오픈 될 때마다 다시 재시작되는 버그가 있었음
        - 안경사/고객의 메세지마다 stepNumber를 적용하여, 1회만 타이핑 애니메이션이 노출되도록 처리함
    - site/simulator로 monorepo 형태로 초기 프로젝트를 세팅을 했는데, 추후 site 자체가 사라져서 오버엔지니어링이 되어버리고 말았다.
    - 백엔드의 API가 개발 테스트 시작일까지 나오지 않아..굉장히 야근을 하면서 진행했던 기억이 난다..
내가 결정하고 구현한 내용: '문제'를 보고 알아서 채워주기
결과(Before → After): '문제'에 적은 내용을 보고 알아서 채워주기
공개하면 안 되는 정보: '가상 피팅' 이라는 단어가 외부에 공개되면 안 됨
```

### 2. Cre8or Club Sentry 모니터링

기능 개발을 넘어 운영 안정성과 팀 대응 체계를 만든 사례지만 현재는 결과 근거가 부족하다.

- 구축 기간과 담당 범위: 2026.03
- 추적한 오류·성능 지표와 주요 알림 조건:
  - Web Vitals(LCP/INP/CLS), HTTP 요청 실패율, 주요 화면 성능, 오류 발생 추이, 네이티브 플랫폼별 오류, 화면별 오류, 영향받는 사용자 수, 처리되지 않은 오류 등의 지표를 추가함
- Slack 알림 전후 장애 인지·대응 시간 변화
  - CS가 들어오거나, 기획팀에서 모니터링 하다가 발견되어야 대응할 수 있었는데, slack 알림에 연동되어 이슈가 발생하면 빠르게 수정 조치 할 수 있었음
- 실제 발견하거나 해결한 대표 장애 수
  - 프로필 첫 화면에서 원본 GIF 및 고용량 이미지를 직접 불러오면서 FSP가 3초를 초과하는 문제가 있었습니다. 서버에서 내려주는 최적화된 썸네일을 우선 사용하도록 변경해 초기 이미지 다운로드와 디코딩 비용을 줄였습니다. (FSP: 3초 이상 -> 1.3초 이하)
- 단독 작업인지, 팀 작업이라면 인원과 기여도
  - FE 3 / Sentry 대시보드 작업 / 10%

### 3. 논마이아큐브 프로모션

프론트엔드 범위를 넘어 서버 로그와 Spring Security까지 분석한 강한 문제 해결 사례다.

- 1~5차의 정확한 기간과 각 차수의 차이
  - 1차: 2024.08-09 (2주)
    - 본인인증(드림시큐리티) 연동
    - 네이버 OCR 스캔 API 연동
  - 2차: 2024.11 (5일)
  - 3차: 2025.01 (5일)
  - 4차: 2025.07 (5일)
    - 2-4차는 1차에서 UI 레이아웃과 제품만 변경됨
    - 4차: aws text scan으로 API 변경
  - 5차: 2026.04 (2주)
    - JSP로 된 페이지에서 HBS로 된 프로젝트로 옮김
    - Web Components 를 사용하여 구조를 변경함
    - 기존 원 페이지형태에서 Step by Step으로 페이지 레이아웃 변경
- 팀 구성과 본인 기여도: 기획 1, BE 1, FE 1 / 100%
- LOT 스캔 건수, 참여 안경점 수 또는 캠페인 규모
  - 300만원이 넘는 스캔이 invoice로 발생됨
  - 참여 안경원 수: 70여곳
- OCR 변경 이유와 인식률·운영 안정성 변화
  - 네이버 OCR의 경우, AI 를 통해서 학습 시킨 후 LOT 제품을 읽도록 하는거였는데, 가격도 비싸고 제품이 변경되면 학습시킬 제품의 스캔본을 재등록 해야해야했다. (그 과정에서 APP KEY 변경도 해야했음)
  - AWS 텍스트 스캔 기능은 서버측에서 업무를 담당해서 업무 비중이 줄어듬
- 임시 조치 이후 백엔드팀의 정식 개선 완료 여부
  - 인프라팀과 협력하여 인바운드/아웃바운드 처리를 따로 한 걸로 인지하고 있음

## 기존 항목 보강 권장

### 안경사 통합관리 시스템 리뉴얼

- 전환한 화면·기능 수와 전체 범위: 화면 60개 이상(안경사용, 관리자 6개의 롤에 따른 화면까지)
- 15,000줄 전환 후 빌드 시간, 장애, 수정 시간 등 확인 가능한 전후 변화
  - 기존엔 운영 배포 시에 20분 걸리던걸 1분 30초만에 배포가 가능해졌다.
  - 장애가 발생해도 기능별 결합도가 낮아져 장애 대응이 빨라졌다.
- 배너 동적 관리로 줄어든 배포·운영 작업
  - 배너를 추가할 때마다 if 날짜 조건을 통해서 구현해야했는데, 백엔드에서 DB로 관리하게 되어 프론트에서 할 일 없어짐
- 파트 리더로 내린 핵심 의사결정과 팀에 남긴 문서·규칙
  - 제품판매: 최대 혜택 관련 프로세스
  - 서브배너, 롤링배너 관련 강제 사항
  - 안경사와 관리자의 페이지 라우터 규칙
  - 토스 페이먼츠 결제 프로세스 (고객 카드 등록 프로세스 - 성공/실패)
  - 이미지 파일 등 정적 리소스 S3 관련 파일 업로드 규칙 (.webp, gif/webm/mp4 등은 무조건 S3 업로드 처리, 페이지 내 모든 이미지 파일을 합쳐 20MB 넘는 경우 무조건 S3 업로드하여 사용)
  - 기타 보안 관련 규칙: 인증 처리 방법, robots.txt 등

### 스마트피팅 -> "모바일/태블릿 전용 착용 렌즈 계산기"

## 작성 템플릿

프로젝트마다 다음 형식으로 답하면 PDF용 문장으로 정리하기 쉽다.

```text
기간:
팀 구성 / 역할 / 기여도:
사용자 또는 운영 규모:
문제:
원인 확인 방법:
내가 결정하고 구현한 내용:
결과(Before → After):
공개하면 안 되는 정보:
```

정확한 수치가 없으면 추정하지 말고 `측정하지 않음`으로 표시한다. 대신 코드 규모, 화면 수,
팀 규모, 대응 기한처럼 확인 가능한 범위를 기록한다.

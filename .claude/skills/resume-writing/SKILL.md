# 이력서 작성 기준

이 저장소의 이력서(`/print`), 경력 상세, 포트폴리오(`/portfolio`) 문구를 쓸 때 따르는 기준.
사실 데이터의 출처는 항상 `~/career-wiki` 이며, **기록에 없는 수치나 성과를 만들어 쓰지 않는다.**

## 0. 쓰기 전에 JD부터 읽는다

가장 먼저 할 일은 지원할 회사 채용 공고의 **직무 요강(JD)** 확인이다.
"이 회사가 어떤 직무를 원하는가", "어떤 역량을 가진 지원자를 찾는가" 두 가지를 기준으로
내 경험 중 **셀링 포인트**를 골라낸다.

> **'내가 보여주고 싶은 것'이 아니라 '회사가 확인하고 싶어 하는 경험'을 중심으로 쓴다.**

이 저장소의 이력서는 특정 공고용이 아닌 기본형이다. 특정 회사에 낼 때는 이 기본형에서
**JD와 먼 항목을 덜어내고 가까운 항목을 위로 올리는 방식**으로 파생시킨다.

## 1. 문서마다 성격이 다르다

| 문서       | 포커스           | 목적                      | 작성 팁                             |
| ---------- | ---------------- | ------------------------- | ----------------------------------- |
| 이력서     | **What**         | 소속/경력 히스토리 확인용 | 있는 그대로 팩트 중심, 간단 요약    |
| 경력기술서 | **How + Result** | 성과 중심, 핵심만 강조    | KPI·문제 해결 중심으로 간결하게     |
| 자기소개서 | **Why**          | 스토리 + 관점 + 지원동기  | 경력기술서 내용을 스토리로 풀어내기 |
| 포트폴리오 | 보여주기         | 시각적으로 어필           | 경력기술서 + 이미지로 구성          |

HR은 자기소개서보다 **경력기술서를 먼저** 본다. 그리고 이력서 한 부를 **30초 안에** 훑는다.
한 항목은 **5초 안에** 무슨 얘기인지 파악돼야 한다. 내용이 좋아도 빼곡하면 서류에서 걸러진다.

**1차 서류 검토는 대개 인사 담당자가 한다.** 업무 담당자가 아니면 모를 전문 용어를 나열하면
내용이 전달되지 않는다. 기술 용어는 남기되 **무엇을 위한 것인지 일반적인 언어로** 함께 적는다.

> ❌ Headless 구조로 통합
> ✅ 입력·검증 로직을 화면과 분리한 공통 구조(Headless)로 통합해 중복 구현 제거

**같은 사실을 두 섹션에서 반복하지 않는다.** 경력 요약 표가 히스토리를 담당하면
자기소개는 관점만 쓴다. 팀 리드 섹션이 있으면 자기소개에서 팀 규모를 다시 나열하지 않는다.

## 1-1. 첫 줄에 정체성을 선언한다

경력 요약 첫 줄에 **핵심 정체성을 먼저 선언**한다. 여러 영역을 다뤘더라도 5:5로 나열하면
깊이가 없어 보인다. "백엔드 기반의 풀스택 개발자"처럼 무게중심을 밝히고, 나머지는
프로젝트에서 "API 스펙 설계 단계에서 소통 비용 절감" 같은 구조적 기여로 보여준다.

## 2. PAAR — 항목 하나의 기본 골격

2026년 채용에서 면접관이 보는 것은 "무엇을 만들었는가"가 아니라 **"왜 그렇게 만들었는가"**다.
특히 **대안 검토(Analyze)** 가 있는지를 본다. AI로 코드 작성이 쉬워질수록 기술적 의사결정이 차별점이 된다.

| 단계 | 항목    | 써야 할 내용                                     |
| ---- | ------- | ------------------------------------------------ |
| P    | Problem | 왜 이 문제가 중요했는가                          |
| A    | Analyze | 어떤 선택지를 검토했고 **왜 이 방법을 골랐는가** |
| A    | Action  | 실제로 무엇을 실행했는가                         |
| R    | Result  | 무엇이 달라졌는가 (**수치 필수**)                |

이 저장소의 `문제 / 조치(처리) / 결과(효과)` 3단 구조는 PAAR의 압축형이다.
**Analyze가 빠지기 쉬우니 조치 문장에 "왜 그 방법을 골랐는지"를 한 조각이라도 남긴다.**

> Memcached 대비 데이터 구조 유연성을 고려해 Redis 선택
> SSR 전환보다 번들 최적화를 우선 적용
> SaaS 도입 대비 데이터 보안·커스터마이징을 우선해 자체 개발 선택

## 2-1. 항목 하나의 구성 요소

| 항목             | 작성 내용                                                  |
| ---------------- | ---------------------------------------------------------- |
| 프로젝트명       | 무엇을 했는지 명확하게                                     |
| 기간             | `YYYY.MM - YYYY.MM`                                        |
| 투입 인원·기여도 | `투입 n명, 기여도 n%` — 규모 안에서 내 몫이 어디까지였는지 |
| 배경             | 목표 또는 당시 문제                                        |
| 성과             | 직무 핵심 지표(KPI) + 수치                                 |
| 역할             | **[문제 해결] [생산성] [의사소통]** 세 관점                |
| 기술·툴          | 실제 사용한 도구·언어·시스템                               |

**역할란은 성과에 담기지 못한 HOW를 담는 곳이다.** 세 관점 중 하나에만 몰리지 않았는지 본다.
실제 문서에는 `[문제 해결]` 같은 괄호 표기를 쓰지 않고 내용에 녹인다.

- **[문제 해결]** 무엇이 막혀 있었고 그걸 어떻게 뚫었는가
- **[생산성]** 반복·중복을 어떻게 줄였는가 (공통화, 자동화, 문서화)
- **[의사소통]** 누구와 무엇을 조율했는가 (기획·디자인·백엔드·운영·경영진)

**기술·툴도 이름만 나열하지 않는다.** 그 도구로 어떤 문제를 풀었고 무엇이 달라졌는지를 한 줄로 붙인다.

> ❌ Figma를 활용한 UI 디자인 및 프로토타이핑
> ✅ Figma 컴포넌트 라이브러리 구축으로 디자인 작업 속도 30% 향상 및 팀 내 일관성 확보

헤드헌터가 권하는 최소 양식은 두 덩어리다. 맨 위에 **[주요 업무]** 로 보유 기술과
프로젝트마다 반복되는 핵심 업무 스킬을 요약하고, 그 아래 **[프로젝트명]** 을 최신순으로 쌓는다.

```
[주요 업무]
- 보유 기술
- 프로젝트마다 반복되는 핵심 업무 스킬

[프로젝트명]
- 기간: 20XX.XX~20XX.XX / 투입 n명, 기여도 n%
- 배경: 목표 또는 당시 문제
- 성과: 목표의 % 달성, 프로젝트 이후 개선된 수치
```

## 2-2. 프로젝트 배치 순서

최근 경력 순으로 두되, **지원 포지션과 직접 연결되는 프로젝트를 상단에** 올린다.
직무와 관련 없는 경험은 삭제한다.

## 3. 탈락하는 3가지 패턴

### ① 기술·프로젝트 과다 나열

주력 기술이 안 보인다. 5년차 기준 프로젝트 **5개 안팎, 최대 10개 이내**로 선별한다
(주니어 1~3년차는 3개 내외). 지원 포지션과 무관한 경험은 과감히 삭제.
프로젝트 수보다 **문제 해결 과정과 기여도**가 중요하다.

여러 프로젝트를 했더라도 맡은 업무와 사용 기술은 크게 다르지 않은 경우가 많다.
**내가 적임자임을 보여주는 핵심만 남기고** 나머지는 지운다. 허전해 보인다고 관련 없는 경력으로
채우는 것은 무의미하다 — 회사의 관심사가 아니다.

### ② 성과 없이 수행 업무만 작성

- ❌ "관리자 페이지 구축, 결제 모듈 개발, 사내 어드민 유지보수"
- ✅ "중복 알림 발송 방지를 위한 Redis 분산 락 구조 도입" / "성과: 어드민 조회 속도 65% 단축"

기업이 궁금한 것은 **결과적으로 무엇이 달라졌는지**다.

### ③ 커뮤니케이션 능력 부재

- ❌ "관리자 페이지 개선 (운영팀과 소통 후 반영)"
- ✅ "운영팀 인터뷰로 '주문 수기 확인' 병목을 정의" / "성과: 운영팀 문의 주 20건 → 6건"

**누구와, 어떤 상황에서, 무엇을 조율해, 어떤 결과를 만들었는지**까지 쓴다.

## 4. 성과는 숫자로

- ❌ 두루뭉술: "효율 개선", "정확도 향상", "안정성 확보", "~할 수 있게 됐습니다"
- ✅ 처리 시간(초), 조회 속도(%), 오류율, 자동화 비중, 문의 건수 감소, Lighthouse·LCP·번들 사이즈

프론트엔드는 로드 타임·Lighthouse 점수·번들 사이즈로 수치를 남기기 좋다.
**수치가 기록에 없으면 지어내지 말고, 대신 규모·범위·기간을 쓴다**
(15,000줄 스크립트 전환 / 렌즈 계산기 3개 통합 / 마커 2만 개 / 약 1년 병행 운영 / 운영 3일 전 기기 변경).

결과 문장은 **수치나 규모를 앞에 두고** 상태 서술을 뒤로 보낸다.
변화량은 `1.2만 → 3.6만`, `1.8초 → 420ms`처럼 **Before → After를 함께** 적으면 검증 가능해진다.

> ❌ 브랜드 인지도를 높이기 위해 다양한 SNS 채널에서 매일 콘텐츠를 올렸고 고객들과 댓글로
> 소통하며 친밀감을 쌓은 결과, 이전보다 훨씬 많은 팔로워가 생겨났습니다.
> ✅ SNS 콘텐츠 운영 최적화 및 커뮤니티 활성화로 팔로워 200% 증대 (1.2만 → 3.6만)

### 문장 형태

전 직무 가이드는 **명사형 종결(~기여, ~단축)로 짧게 끊고 3~5줄로 넘버링**하는 개조식을 권한다.
다만 **이 저장소의 인쇄 이력서는 서술형(~했습니다)** 으로 통일돼 있다. 문체를 바꾸는 것은
별도 결정 사항이므로 임의로 섞지 말고, 어느 쪽이든 **한 항목 안에서는 일관되게** 쓴다.
서술형을 유지하더라도 "한 문장에 하나의 사실", "3~5줄 이내" 원칙은 그대로 적용한다.

## 4-1. 프론트엔드 Before / After 예시

**Before** — 수행 업무 나열

- React 기반 대시보드 화면 개발
- 공통 컴포넌트 분리 및 리팩토링
- 페이지 로딩 속도 개선

**After** — PAAR 적용

- **P**: 초기 로딩 지연으로 LCP 4초 이상 발생, 주요 지표 확인 전 이탈 증가
- **A**: Lighthouse·번들 분석으로 병목 구간 파악, **SSR 전환보다 번들 최적화를 우선 적용**
- **A**: 코드 스플리팅, 이미지 최적화, 공통 컴포넌트 분리, 렌더링 구조 개선
- **R**: 초기 로딩 4.2초 → 1.8초, Lighthouse 성능 58점 → 86점

같은 작업(공통 컴포넌트 분리)이라도 **왜 그 순서로 했고 무엇이 달라졌는지**가 붙으면
판단의 기록이 된다. 이 저장소의 항목들도 이 형태를 목표로 한다.

## 5. 포트폴리오 구성 (원티드 템플릿 기준)

1. **표지/About** — 직무 한 줄 → 강점 문장 2~3개(수치 포함) → 연락처·링크 → Skills
2. **프로젝트마다**: 이름·기간·링크 뱃지(GitHub / Site / Docs) → **대표 이미지** →
   개요(수치 포함) → 역할(불릿) → Skills → 세부 작업별 **AS-IS / TO-BE** → 회고
3. Other Projects(간단 카드) → 오픈소스 기여 → 자격증 / 수상 / 발표

- **이미지를 넣는다.** 어떤 프로젝트였는지 이미지를 보여주면 인사담당자가 이해하기 쉽다.
- **AS-IS / TO-BE로 전/후를 나란히** 둔다. 이 저장소는 `beforeAfter` 필드로 구현돼 있다.
- 자세한 내용을 볼 수 있는 링크를 붙인다. 단 **클론 코딩 저장소, `fix`·`update` 같은 커밋 메시지가
  쌓인 저장소는 붙이지 않는다.** README에 아키텍처·기여도·기술적 의사결정 이유가 있어야 한다.

## 6. 작성 후 체크리스트

- [ ] 각 항목에 Problem / Analyze / Action / Result가 다 있는가 — 특히 **Analyze(왜 그 선택)**
- [ ] 결과에 수치 또는 구체적 규모가 있는가
- [ ] "~할 수 있게 됐습니다" 같은 상태 서술로 끝나는 결과 문장이 없는가
- [ ] 협업 항목에 상대·쟁점·결과가 드러나는가
- [ ] 다른 섹션과 같은 사실을 반복하지 않는가
- [ ] 기술 나열이 주력 기술을 가리지 않는가
- [ ] 역할이 [문제 해결]·[생산성]·[의사소통] 중 한쪽에만 몰려 있지 않은가
- [ ] 변화량을 `이전 → 이후` 형태로 적을 수 있는 것이 있는가
- [ ] 지원 포지션과 가장 가까운 프로젝트가 위에 있는가
- [ ] 30초 안에 첫 항목의 결론이 읽히는가, 한 항목이 5초 안에 파악되는가
- [ ] 개발자가 아닌 인사 담당자도 무슨 일인지 알 수 있는가
- [ ] 프로젝트마다 기간·투입 인원·기여도가 있는가
- [ ] 모든 수치가 `~/career-wiki`에 근거가 있는가
